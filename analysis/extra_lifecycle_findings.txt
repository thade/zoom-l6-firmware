L6 ADDITIONAL PAD RECORDING: FILE LIFECYCLE
3 October 2026

Scope
The normal clean input files AND processed MASTER remain ordinary recordings.
This work adds the lifecycle of the separate pre-master stereo pad file. It does
not change their paths, substitute their samples, or move/copy their master.

Result
A compiled offline state machine now creates a unique file inside a selected
SOUND_PAD/PADn folder, writes a private WAV header, arms the capture, drains it on
stop, finalizes and closes the file, reopens and verifies it, and only then exposes
a verified path. Eleven lifecycle groups pass, including 16 injected file-operation
failures. The previous eleven extra-capture groups also pass with the rebuilt ELF.
Original L6 WAV parser 0x8000f0b0 accepts the private header and recovers the exact
stereo float32 format and sample count in an independent emulator test.

Nothing is installed on the L6. Public filesystem calls are modeled with in-memory
files; original parser and new compiled state machines execute. Timing hooks,
producer/worker fences, catalogue assignment and persistence remain unbound.

State sequence
IDLE -> ARMED -> CAPTURING -> DRAINING -> FINALIZING -> VERIFYING -> VERIFIED
Any failure leads to FAILED. A failed instance cannot be automatically restarted;
resource recovery must first be audited. A verified instance also cannot be reused
implicitly. No catalogue or existing pad assignment is changed in any state.

Preparation
life_prepare requires a zero-initialized, unused lifecycle instance and externally
quiescent capture/consumer. It disables capture before file preparation. It builds
and owns a UTF-16 path such as A:\SOUND_PAD\PAD1\OD_00000001.WAV. Pad indices are
restricted to 0..3. Creation uses stock open API 0x8005ffe8, flags 0x501 and
attributes 0x80 (exclusive-create semantics established in earlier filesystem
investigations). A collision advances the hexadecimal serial and tries again,
with a maximum of 32 attempts and no serial wrap. Other open errors stop work.
Existing files are never overwritten or removed. The filesystem behavior for
these tests is modeled at the public API, not newly executed against FAT media.

Private WAV metadata
Each lifecycle owns its header and readback buffer, avoiding the stock global
format/header workspace during prepare/finalize. Header layout:
  RIFF/WAVE, 16-byte fmt payload, IEEE float format tag 3,
  stereo, 48000 Hz, 32 bits/sample, 384000 bytes/s, 8-byte block alignment,
  JUNK padding, and data starting at byte 512.
No BEXT/other optional metadata is included in this prototype. Parser acceptance
is established offline; complete pad-loader and hardware playback are not.

Start and stop
Preparation leaves capture disabled. life_start_quiesced enables it explicitly;
life_stop_quiesced disables it and enters DRAINING. These function names describe
PRECONDITIONS, not implemented exclusion: callers must prevent future producer
access, await an in-progress producer and serialize against the file consumer.
They are not yet connected to ordinary record start/stop, and sample-aligned
boundaries are not demonstrated on hardware. life_step refuses to finalize a
still-armed or capturing session.

Drain/finalize/verify
life_step advances incrementally, with at most one 4-KiB audio write or readback
per call. After the capture is stopped and every owned block has been written,
it updates RIFF/data lengths, seeks to offset zero and checks the complete header
write. It closes the write handle, reopens the owned path read-only, checks exact
file length/header, and reads the entire audio payload in bounded pieces.

capture.c now maintains a rolling 32-bit FNV-1a checksum over each successfully
written payload batch. Readback must produce the same checksum. The checksum
is for accidental corruption detection, not cryptographic authenticity or a
mathematical proof of byte identity. Exact payload bytes are independently checked
against known samples by the host tests. Readback incurs a full extra-file read
before assignment eligibility; this can take time on whole-song recordings.

A successful final verification read is followed by a checked read-handle close.
Only VERIFIED makes life_verified_path return a path; every earlier/failed state
returns null. This is eligibility for a later assignment operation, not an
assignment or a guarantee of power-loss durability.

Failure/cancellation behavior
Short/error header writes, audio writes, seeking, close, reopen, info, header reads,
audio reads and read-handle close all prevent eligibility. A close failure is
marked uncertain and the instance is quarantined; it is not retried blindly,
since the public close may already have invalidated the handle.

Cancellation at ARMED, CAPTURING, DRAINING, FINALIZING or VERIFYING requires both
participants already quiesced. It disables further capture/drain and closes any
owned handle. Partial/failed files are retained unassigned for later recovery.
No automatic deletion or attempts to restore/truncate an existing file occur.

Evidence
- Successful lifecycle in all four pad directories, correct independent format,
  expected sample payload, checked close and no open modeled handles remaining.
- Collision advances to a new name and preserves old backing bytes exactly;
  32 occupied names, serial exhaustion and invalid-pad rejection covered.
- Empty recordings and repeated/out-of-order start/stop calls rejected.
- Sixteen IO failures, corruption of header/sample/length/trailing data, and
  cancellation at each live phase never expose an eligible path.
- Ordinary file sentinels, stream-control memory and stock format workspace stay
  unchanged during lifecycle tests. The earlier extra-capture suite separately
  executes all seven stock file writers alongside the extra capture.
- Original WAV parser accepts the independently generated 512-byte header and
  returns 192 frames for a three-block test recording.

Resource change
Capture state now includes a 4-byte write checksum, bringing its total to 65,564
bytes (64 KiB samples plus 28 bytes state). Lifecycle adds owned path, header,
4-KiB readback buffer and state; exact sizeof is recorded in the JSON report.
CPU cost of checksumming, SD latency, memory placement and available headroom
remain unmeasured. File-size limit still faults rather than implementing splitting.

Next integration boundary
Bind prepare/arm/start and stop/drain to ordinary record events without delaying
or redirecting the ordinary recorder. Implement and verify actual producer AND
consumer quiescence, and schedule the extra writer/readback with existing storage
work. Then pass only VERIFIED files into the earlier checked pad assignment path,
with pad reader exclusion, loader readback and settings persistence. Keep previous
backing selected until that separate operation succeeds. These bindings are not
satisfied merely by the lifecycle phase reaching VERIFIED.
