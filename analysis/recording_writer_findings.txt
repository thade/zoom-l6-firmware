L6 PRE-MASTER TAP: RECORDING SCALE, WAV WRITER AND DESTINATION
3 October 2026

Result
Nine additional offline groups pass. Original instruction windows/functions
carry a modeled pre-master snapshot through the stock scaling, stereo reader,
record-stream producer, queued file-access worker and WAV finalizer. The result
is an in-memory WAV whose samples match the intended live-plus-pad mix. The
master-level-adjusted monitoring buffer and tested input buffers are unchanged.

The core sample-to-WAV route is now exercised, not just the ring reader. This
still excludes full recorder start/stop, compressor/effects bodies, post-record
processing, actual SD IO and concurrent scheduling. No device was accessed and
no patched firmware or compiled capture hook was produced.

Evidence files

1. Actual scaling resolves the previous unity assumption
Original instruction 0x20227622 loads S18 from the literal at 0x202274e8.
The bits are 0x30000000, float 2^-31 (approximately 4.656612873e-10).
Original master enqueue window 0x2022a55a..0x2022a77a uses this scaling on the
stereo staging samples before placing them in recording rings 10 and 11.

The older tap tests deliberately supplied unity to isolate routing. Their sample
magnitudes were synthetic internal values, not verified normalized WAV levels.
This test executes the original literal load, seeds internal values in the
+/-2^31 convention, and checks resulting normalized float32 WAV values.
For example, internal +2^30 and -2^29 become WAV +0.5 and -0.25.

Five distinct 64-frame stereo blocks include silence, signed ramps, full-scale
and above-full-scale values, and source-ring wrap. The stored samples remain
bit-exact for these binary-exact fixtures. Values above +/-1 survive without
clipping in this recording path. That does not mean the monitor output avoids
clipping, or that every earlier DSP stage is linear/unclipped.

2. Original producer/queue/writer chain
Startup at 0x8000ada2..0x8000adaa registers callback 0x80002831 with setter
0x80038258. This setter stores it at 0x8077ca30+0x5a8. The test runs the setter.

Original producer 0x80038e60 derives two channels from the stream stereo mask
and four bytes/sample from the 32-bit stream metadata. At 0x800390b8 it calls
0x80002830, which forwards to ring reader 0x80018fd0. Observed arguments confirm
stream index 10, two channels, four bytes/sample and 64 frames for each block.

The producer accumulates incomplete sectors, sends complete 512-byte sectors
through stock callback 0x80037590, and alternates staging buffers. That callback
submits a four-word message to the file-access queue:
  operation 0, stream index, payload pointer, byte count.
The queue transport/semaphores are modeled; submission instructions execute.
The test drains each queued block before proceeding, so this is not a proof of
buffer lifetime under arbitrary scheduler delay.

Original worker 0x80037380 receives those messages, resolves the per-stream file
handle at 0x8077ca30+0x1e4c+index*4, and calls public write API 0x800622b0.
Only public filesystem operations are replaced by in-memory implementations.
The worker's original short-write check and error-state update execute:
  successful status but short transfer -> error 0xffffd826;
  injected IO error 0xffffd825 -> same error retained.
This does not establish that every upstream stop/assignment path respects it.

The independent mono-stream fixture requests index 0, one channel and four
bytes/sample. A 64-frame block contributes only 256 bytes, so no write is queued
until a second block completes the sector. Both blocks survive in order.

3. WAV creation and finalization
Original format builder 0x8000fb68 produces the fmt chunk with:
  format tag 3 (IEEE float), 48000 Hz, 32 bits/sample,
  two channels, block alignment 8, byte rate 384000 for the stereo fixture.
Original header writer 0x8000fc68 writes RIFF/WAVE, this fmt chunk, padding and
a data header. Synthetic arguments select a 512-byte data start; production
BEXT/other optional metadata is omitted from this fixture.

Original finalizer 0x8000ea08 updates RIFF and data lengths using the modeled
filesystem. A separate host chunk parser verifies lengths, format and exact
sample payload. The five-block file has 320 stereo frames. The report records
its SHA-256. These are short synthetic fixtures, not whole-song stress tests.

4. Actual capture path differs from final recording path
The original file-creation path at 0x8000438e calls 0x80022bb8, which obtains the
current segment number and invokes 0x80023640. The creation call at 0x800043a2
uses flags 0x102 and attributes 0x180.

Initialization 0x8000440e..0x80004416 passes the original UTF-16 string "Work"
at 0x800a32e0 to 0x80022e50, which sets the subdirectory used by 0x80023640.

With a synthetic take directory, original builders and the actual creation-call
window produce, for example:
  recording: A:\RECORDER\261003_120000\Work\MASTER.WAV
  final:     A:\RECORDER\261003_120000\MASTER.WAV
Input tracks use the same distinction. Tests cover streams 0, 2 and 10, segments
1 and 2. The report contains exact names. Segment selection metadata is modeled;
path assembly and the creation-call arguments execute as original code.

The final-path builder 0x80022c80 alone is therefore NOT the initial writer's
path selector. Both path builders share storage; queued work needs owned paths.
The Work subdirectory and take directory are shared across streams, so changing
either globally would also relocate input tracks.

5. Implication for direct pad recording
The data writer is largely destination-independent once it has a file handle.
A master-only file handle pointing into a pad folder could therefore reuse the
existing sample writer. However, merely redirecting its initial open would break
later code which reconstructs Work and final paths. Post-processing 0x80004868
also contains audio processing/replacement branches; it has not been executed
end-to-end against this new capture source.

A complete change must own the master file's lifecycle: unique creation, split
segments, final header/close, any intended post-processing, and assignment after
success. Input streams should retain their ordinary lifecycle. The stock open
flags must not be blindly reused for an existing pad filename; a new unique file
and verified exclusive creation are needed for the new destination.

Another option remains recording in Work and moving the completed master to the
pad directory using the existing filesystem rename/move path. Earlier findings
already resolved 0x80060a18 -> 0x80060c48 as FAT-directory manipulation rather
than a full audio-data copy (analysis/firmware_integration_findings.txt). This
could meet the no-large-copy objective with fewer changes to initial recording,
but cross-directory collision, failure and recovery behavior need dedicated
verification. It would relocate the master, not retain an independent copy in
the take folder. No choice between these lifecycle designs is implemented here.

Next concrete implementation boundary
Build an offline master-file lifecycle adapter which records to an owned unique
pad path while retaining ordinary stem destinations, then finalizes and exposes
that file only on success. Audit/replace only master-specific Work-path consumers;
do not turn the global recording target into stock pad mode (that drops stems).
Include split-file and failure paths before connecting it to the capture hook.
The owned capture buffer, effects/alternate audio modes, pad lifetime fence,
real-time performance, firmware acceptance and recovery remain separate open work.
