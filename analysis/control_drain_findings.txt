L6 OPTIONAL-CAPTURE ADMISSION CLOSE AND CONTROL DRAIN
3 October 2026

Result
The separate offline prototype can now close capture request admission, wait
for already admitted callers and callbacks, and obtain acknowledgement of a
marker from the original RecPlayCtl dispatch loop. Later ordinary mixer requests
continue without joining this capture session. This is a control FIFO-prefix
acknowledgement, NOT a queue-empty test or a memory-reclamation fence.

Nine new groups and all 122 preceding relevant groups pass: 131 total.
The exact extra WAV test and ordinary-file sentinel checks still pass. Stock
firmware is unchanged. Nothing was installed or written to the device/card.

Protocol
1. Admit the intended capture STOP request before closing admission. Closing is
   not a stop operation: a later ordinary STOP has no owned optional-capture
   timestamp and cannot be relied upon to finalize that capture.
2. ct_close_admission(transport, session) records the last admitted request ID
   and RecPlayCtl task handle under the existing critical section. Repeat calls
   preserve the original cutoff. New automatic entries obtain no capture Request;
   explicit begin requests are rejected. Earlier held requests can still bind,
   submit their queued work, return and finish after closure.
3. ct_drain_poll waits for router pending=0, empty request/callback scopes,
   no busy/held automatic slots, and every allocated Job to have completed its
   callback, confirmed its send, and released its Request. These checks include
   callers paused before submission, not merely an observed empty queue.
4. When those ownership checks pass, set SENDING before leaving the critical
   section. Acquire the original producer mutex and send a 32-byte marker through
   the stock send wrapper, then release the mutex. Blocking operations run outside
   the critical section. Poll must run on a task other than RecPlayCtl itself.
5. RecPlayCtl executes the compiled marker callback through its original dispatch
   loop. It validates Transport, session, cutoff, tag and worker task identity.
   Acknowledgement requires this callback AND confirmed send/mutex release.
   A callback arriving before send returns cannot report premature success.

Return values: close 0=closed, 12=invalid context/session or missing worker.
Poll 0=control acknowledgement, 10=marker sent awaiting delivery,
11=earlier ownership or marker outstanding, 12=invalid context,
30=sticky uncertain/failed marker acquire/send/release. Poll can block inside
stock mutex/queue operations; it is not a real-time-safe audio callback API.
An uncertain earlier request send retains ownership and keeps poll waiting.
Marker failure is not retried automatically, even if delivery is later observed.
The caller must distinguish a drain error from optional-file success or failure;
control acknowledgement by itself says nothing about the recording's validity.

Stock integration evidence
Original RecPlayCtl dispatch at 0x80034bc8 receives copied 32-byte messages from
queue handle word 0x801f8f38 and calls word 0 with a pointer to the remaining
arguments. The new marker uses this convention and bypasses capture wrapping.
Producer mutex word: 0x80446894; wait: 0x80076950; give: 0x800763d8.
Worker handle word: 0x80446dc0 (RecPlayCtl descriptor 0x800a1e74).
Static inspection of task creation 0x80076d3c..0x80076dc4 shows the same task
control pointer written to the output handle (store at 0x80076d7a) and to the
current-task word 0x808e291c (stores at 0x80076dbe/0x80076dc4). This supports
comparison with the original current-task getter 0x800770e8. It is static
inspection, not execution of complete task creation or physical chip evidence.
The six new transport words increase synthetic Transport storage to 1712 bytes.

New verification groups
1. Queued STOP and caller ownership finish before marker; exact [64,128) WAV.
2. Already admitted producer resumes/submits after close; drain waits for it.
3. Earlier unsubmitted request blocks until its ignored return releases it.
4. Later ordinary playback/stop requests retain stock messages and allocate no
   capture IDs, including another task. A later stock message can remain queued
   while the marker is acknowledged: acknowledgement is explicitly not empty.
5. Wrong session, absent worker, worker polling itself, new explicit admission,
   malformed marker fields and wrong marker task cannot produce success.
6. Uncertain earlier send prevents marker submission.
7. Mutex acquire, marker send and mutex release failures stay sticky; acquisition
   failure causes no send/release and late marker delivery cannot erase error.
8. Marker delivery before sender return, including eventual send failure. Uses
   two independent emulator CPUs with explicit Transport-byte transfer while the
   sender is paused. Peer polling in SENDING returns waiting, not success.
9. Busy entry cookie blocks marker even if the router pending count is zero.

What is still unproved
Kernel queues, mutex outcomes, task switching and deep recorder/file effects are
fixtures. Original request/dispatch code and compiled protocol execute, but this
is not full concurrent RTOS, interrupt, SD or DSP execution. Early-callback tests
are controlled interleavings, not exhaustive schedule exploration.
Observed producer coverage is still bounded by the earlier five-entry audit.
Task handles are assumed stable; task deletion/reuse is not supported.

A marker covers work ahead of it in the modeled FIFO. New ordinary requests can
queue later and continue touching Transport through wrappers. A wrapper can also
have loaded the active pointer before the guarded admission check. Therefore
this protocol alone cannot justify detaching/freeing Transport, changing the
session, or reusing queued Request/Job storage. Replay/unexpected references and
uncovered paths still require a lifetime argument. No teardown or rearm is added.

The audio hook/exchange lifetime and optional-file worker are independent of the
control queue. A successful marker does not prove hooks have stopped using old
pointers, all audio has been consumed, file writes succeeded, or a pad reader is
finished with a file. The existing external-quiescence precondition on retirement
has NOT been discharged by this stage. Safe RAM placement/cache/timing/recovery
and automatic pad assignment remain unproved.

Next bounded step
Design and test an audio-hook detach/acknowledgement protocol that accounts for
hooks already entered or holding a pointer, then combine that with file-worker
completion and this control acknowledgement. Keep old session storage intact
until all three lifetimes are accounted for. Only then consider repeated-session
rearm; no physical firmware experiment is implied by these emulator results.

Follow-up: analysis/session_detach_findings.txt adds a permanent gateway that
reserves hook/worker entry before reading the session pointer and waits for
terminal file-worker completion. Transport/direct-API references remain outside
that fence. No whole-session storage reuse or restart is established.
