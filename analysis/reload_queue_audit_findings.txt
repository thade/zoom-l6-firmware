L6 v1.10 — native queue allocation, dispatch and loss audit
4 October 2026

Conclusion
Keep the original 32-byte assignment queue and 20-byte UI queue. Both can carry
compact reload identity, and the original assignment dispatcher can invoke a
replacement callback without enlarging its message. The 48/36-byte packets from
the preceding experiment are useful for testing but are a poor native layout.
A compact format alone is insufficient: UI filtering and explicit queue clearing
can discard a continuation. Those operations must participate in the ownership
protocol before a native adapter can be considered complete.

Fourteen new audit groups pass. Focused regression: 66 groups across pad_reload,
reload_ownership, reload_transport and reload_queue_audit. No compiled C or ELF
changed this stage. The prior 343-group regression remains recorded separately;
its unrelated suites were not rerun for this audit-only change.

Recovered allocation and task structure
Original initializer 0x80048248 creates 35 tasks from 24-byte table entries at
0x800a1bd4, 86 semaphore-like objects, then eight data queues. Queue handles are
stored at base 0x801f8f1c plus offsets 4 through 0x20. Actual queue allocator
0x80076348 computes depth*item_bytes+0x50, then stores depth at handle+0x3c,
item_bytes at handle+0x40, and current item count at handle+0x38.

0x801f8f24                64           16                   1104
0x801f8f28 (UI)         4096           20                  82000
0x801f8f2c                 1           16                     96

0x801f8f38               512           32                  16464
0x801f8f3c (assignment)  512           32                  16464

The assignment allocation is 0x80048340; UI allocation is 0x800482ec. The
initializer's once-only flag means re-entering it does not resize existing queues.
Queue send 0x800483f8 and receive 0x800483a8 call kernel operations 0x800763d8
and 0x80076710; positive kernel success becomes wrapper result zero.

SamplerFileAssign table row 30: entry 0x80036291, task handle slot 0x80446dc8,
stack depth 0x1000 words (16 KiB). Main row 27: entry 0x8006dd71, handle slot
0x80446da4, stack depth 0x2000 words (32 KiB). The task creator shifts stack
word count by two at 0x80076c66. Creation priorities are table fields, not proof
of eventual runtime priority. Main's wrapper tail-enters 0x8002c1e8 at 0x8006dd8a.
Task creation and heap backing are modeled; these are executed call arguments
and original allocator field writes, not an observed physical RTOS boot.

Why not enlarge the queues?
Changing only the allocation size is unsafe. Assignment worker 0x80036290
reserves exactly 32 stack bytes, receives into them and calls message word zero
with a pointer to the following 28 bytes. UI sender, receiver, backlog arrays,
cleanup routines and main-loop buffers copy or stride exactly 20 bytes.
The old queues truncate 48/36-byte packets; enlarged queues would overrun some
existing buffers unless every affected caller and buffer changed too.
At unchanged depths, enlargement alone would add 8 KiB assignment storage plus
64 KiB UI storage (72 KiB total), before any other buffer changes. Available
hardware heap headroom is not established by this arithmetic.

Candidate compact formats (not yet implemented as compiled native adapters)
Assignment, eight words / 32 bytes:
  replacement callback, RL_MAGIC, owner, worker-child, RL_WORKER, 0, 0, 0
The original worker's BLX at 0x800362b4 already supports a replacement callback.
Its 28 argument bytes fit the 16-byte envelope. The known original reload callback
0x80049da0 ignores its incoming argument payload, so it does not need an extra
allocation to preserve payload. This claim does not extend to other callbacks.
The replacement callback must validate tickets and obtain its permanent runtime
and task context from a trusted binding, rather than trusting arbitrary pointers
in queue data. Busy metadata must retain work without dropping it or replaying
stock work that already returned.

UI, five words / 20 bytes:
  1, 4, 26, owner, UI-child
The header retains stock routing; the final two words carry non-reused ledger
identity. Original sender 0x8006e4b8 and receiver 0x80020690 preserve all five
words. For this kind-1 event, receiver returns without the coalescing path used
for other event classes. All five main-loop routes call 0x8002d568 for kind 1:
call sites 0x8002c252, 0x8002c3be, 0x8002c3ca, 0x8002c42a, 0x8002c436.
The reload branch uses 0x8002d74c -> 0x80008b68 -> refresh 0x8000a5d8.
Its category dispatcher loads word three, but the event-26 branch does not use
that value as a pad index or pointer. Tests with nonzero ticket words take the
same branch. A compact decoder should reconstruct the original zero-payload
event before calling it, to make the supported contract explicit.

Queue loss and filtering
1. Automatic backlog compaction:
   Sender 0x8006e4b8 reads queue count through 0x800483a0. At >=4096 it drains
   20-byte events into 0x808cc524, calls 0x8001fd08, and re-enqueues survivors.
   The duplicate pass compares all five words for kind-1 messages. Two stock
   [1,4,26,0,0] events become one. Distinct owner/child pairs survive; duplicate
   copies of the same ticket merge. A test starts with a real modeled depth of
   4096 (4094 stock duplicates and two distinct tagged events) and executes this
   entire original path, preserving both tagged events and the new event.
2. Explicit backlog cleanup 0x80020360 uses the same reducer even when the queue
   is not full. Both filter call sites inside it and both inside the full-queue
   sender need to be covered by any ownership-aware reducer binding.
3. Reducer 0x8001fd08 also has broader rules. Later kind-2 messages, or kind-0
   category-6/7 messages, can delete earlier entries by event code alone. Crafted
   same-code inputs prove that even distinct reload tickets can be discarded.
   This establishes filter semantics, NOT that normal input devices actually
   generate those particular same-code combinations during a reload.
4. Targeted deletion 0x80020548 drains and re-enqueues except entries matching
   its first three selector words. Payload/ticket words are ignored. Calling
   it with (1,4,26) removes both tagged reloads. Existing direct callers have
   been located, but this test does not assert they request that tuple today.
5. Whole-queue flush 0x80020438 drains all events and re-enqueues none. Its direct
   caller 0x8002c4a2 is on the Main startup/mode-5 route. It drops tagged reloads
   regardless of layout. We have not classified that mode as a particular
   physical device mode here or demonstrated a live hardware overlap.

A combined negative test constructs two real compiled reload owners/branches,
then passes their candidate ticket events through the original whole-queue flush.
Both owners remain BUSY and publication remains blocked. This is safe retention,
not recovery or successful completion: the dropped continuations need an explicit
policy. The ownership protocol must never infer completion merely from empty
queues or clear its state to make progress.

Recommended next implementation
Implement and test a compact compiled sender/decoder using the existing queue
widths and original worker/Main dispatch. Bind task attribution to the recovered
Main/SamplerFileAssign identities and original current-task getter, with lifecycle
and interrupt-context checks. The current emulator's selected-context fixtures
are not an adequate native binding by themselves.
Alongside this, define ownership-aware cleanup: preserve pending owned events
through filtering, and either defer destructive clears until work joins or record
an explicit failed/cancelled continuation while retaining any outstanding work.
Do not wait for Main to service an event while blocking that same Main task, and
do not release an owner while a worker could still publish its UI continuation.
The cancellation/recovery policy remains to be implemented and tested. Ordinary
recorder, USB/card lifetimes and asynchronous prefetch still need their earlier
separate ownership bindings. No deployable patch is claimed by this audit.
