Original getters 80067050 and 80053b68 return these pointers only for class 1;

This is not a claim that no other code can subsequently modify those globals.

USB worker supplies internal buffer ranges
-------------------------------------------
Original UsbPollingTask 80045cf0 builds the configuration for selectors 5..10,
covering the six previously recovered audio/storage configurations. Its event
wait, startup helpers and peripheral effects use the established scheduling
fixtures. The request is captured at 8003b5a8, before USB starts. Its original
construction executes; no buffer pointer is inserted by a fixture.

The wrapper adds 4 to the request address; 8003aeb8 passes that object+38 to
80067980. Tests preserve the captured request in separate synthetic storage and
execute 80067980 plus the original 80066f18 getters. All six configurations
install the same five base/length pairs at [808e0d1c,808e0d44):

  Provider index    Base        Length      Base + length
       0          20003200       1536         20003800
       1          20003800         12         2000380c
       2          2000a420       1536         2000aa20
       3          20000200      12288         20003200
       4          20003820      27648         2000a420

These provisioned ranges total 43,020 bytes within the already measured 128-KiB
DTCM mapping. This is address-placement evidence, not a new spare-memory total
or physical DMA-reachability test. The buffers are not candidates for capture.

Original audio-state constructor 80070068 then consumes provider IDs 3 and 4,
placing their bases and table pointers into the states at 808e2f80 and 808e2e54.
Execution stops before 80070298. That routine calculates frame sizes, ring
lengths and clearing sizes from format/rate inputs; those resulting spans and
later wrap/transfer paths remain the next bounded audit. Merely installing a
small base/length pair does not prove later arithmetic respects it.

Alias evidence and remaining decision
-------------------------------------
Original MPU programming puts both ends of both candidate gaps under the same
highest-priority region 10: [80000000,82000000), TEX=0,S=0,C=1,B=1, full access.
This extends the existing map check to the actual candidate boundaries. It is
a cache/access-attribute result, not address translation or alias exclusion.
The live SEMC evidence still gives one valid 32-MiB decode window; it does not
measure fitted density or guarantee that different addresses select different
physical cells. No physical/cache behavior is simulated by these tests.

Unchanged passive fingerprints cannot settle that distinction. No safe writable
locations in the gap have yet been established, so a destructive pattern test
there would assume the ownership it is meant to prove. Chip/BOM evidence or a
controlled address-independence test with independently owned locations remains
necessary for a stronger physical conclusion.

Next: trace 80070298 and later USB endpoint/transfer destinations, including
mode changes. Population of the eight-pair table ending at 80960078 and missing
bootloader ownership remain unresolved. Do not repeat unchanged passive sweeps
as a substitute. Keep extra capture disabled and retain the current history
layout until the ownership/physical questions are resolved. The pre-compressor
recording remains the preferred feature; this audit supplies no reason to pivot
to recording only the processed master.
