ZOOM L6: RECORDING FINALIZATION AND LIVE PAD CATALOGUE INSERTION
Investigation: 2 October 2026

RESULT

The stock firmware contains the main building blocks needed for an automatic
record-to-pad feature: recording shutdown and WAV finalization, post-record
processing, adding a filename to a pad's in-memory catalogue, and assigning that
entry. Catalogue insertion does not require a complete directory rescan or USB
File Transfer Mode. This materially strengthens the feasibility of a targeted
firmware change; it does not establish that modified firmware can be installed
or recovered safely.

The missing connection is between an ordinary multitrack recording's finalized
master and the destination pad folder. The existing after-record assignment
helper cannot simply be given an arbitrary RECORDER path: it strips that path to
its basename, finds the name in the pad catalogue, and reconstructs a path under
the pad's directory. Copying the finished master into a pad folder is therefore
the most conservative initial design for retaining the original recording.

NEW OFFLINE VERIFICATION

13 cases passed using unmodified stock instructions in Unicorn. For each of four
pads, the tests initialized a synthetic empty catalogue using stock routines,
inserted two names with the stock insertion function, checked counts and paths,
then executed the stock post-record assignment helper. That helper resolved the
second entry and reached the intercepted audio assignment operation with the
expected pad, path, count and index. Its settings-save branch was also reached.

Negative cases checked that an absent filename did not reach assignment. A
RECORDER path with a basename already present in the catalogue selected the PAD
file, confirming that this helper is not an arbitrary-path assignment mechanism.
The final case executed the stock basename builder and confirmed logical
recording stream 10 produces MASTER for file number 1.

Only RAM catalogue, lookup, string and control-flow behavior was executed. RTOS
locks, notifications, settings persistence and actual audio assignment were
intercepted. No SD filesystem, audio, complete recording, reboot or firmware
update was emulated. No commands were sent to the connected mixer this turn.

RECORDING STOP SEQUENCE (STATIC EVIDENCE)

0x8004ba40 RecStop worker callback
  Reads signed recording target at 0x801f5f00. A negative target follows ordinary
  recording behavior; a nonnegative target identifies a pad. Passes that target
  to 0x8000b698 at 0x8004ba7a, then performs subsequent recorder/UI cleanup.

0x8000b698 stream shutdown/finalization
  Contains waits on stream-state predicates before finalization. In the active
  recording branch, calls 0x8000ea08 then 0x8005c1f8 for each nonzero stream file
  handle, logical indices 0..11. The index-10 pair is at 0x8000b8e2/0x8000b8e8.
  After this block, conditionally calls post-processing 0x800032b0 at 0x8000b978.
  This establishes instruction ordering, not independently verified SD durability
  or a complete error-handling contract.

0x8000ea08 WAV chunk-size finalizer
  Recognizes RIFF, WAVE, bext and data; updates RIFF/data size fields using file
  operations. This supports interpreting the preceding sequence as finalization.

0x800032b0 post-record processing
  Walks logical streams 0..11, checks their state, and calls 0x80004868 with the
  logical stream, recording target and output-path buffer. Output buffers begin
  at 0x8060e504 with a 0x20a-byte stride. Logical stream 10 uses +0x1464.
  At 0x80003550, only a nonnegative target and nonempty stream-10 output path
  lead to 0x80008bd0(target, path). Ordinary recording skips this assignment.

0x80004868 substantial post-processing routine
  Handles file/segment operations and conditionally chooses pad versus recorder
  destinations. Positive-target branches get the pad directory via 0x80008e58,
  build a destination via 0x80048988, perform a two-path filesystem operation
  at 0x80060a18, then insert the filename via 0x80008dd8. Examples at
  0x800052bc..0x800052fe and 0x8000566c..0x800056aa.
  The filesystem operation appears to be rename/move, but its final indirect
  filesystem driver implementation was not recovered in this pass. Do not treat
  this as a verified copy routine or reuse the whole branch blindly: this large
  routine also contains audio processing and file replacement paths.

0x80023258 recording basename builder
  The branch at 0x80023338 identifies stream 10 and loads the UTF-16 MASTER label.
  0x800235d0 (wrapper 0x80022c80) builds a recording path and appends .WAV.
  Returned paths use shared storage; any asynchronous operation needs its own
  copy of the path before other firmware calls reuse that storage.

PAD CATALOGUE AND ASSIGNMENT CONTRACTS

Catalogue address = 0x8023e398 + pad * 0x80950, with pad 0..3.
Directory string is stored inline at catalogue+0x14. Filename entries start at
catalogue+0x2a4 with 0x20e-byte stride. This clarifies earlier wording describing
the directory as a pointer: the getter RETURNS a pointer to that inline string.

0x80008f40 builds and scans all four SOUND_PAD/PADn directories.
  Uses 0x80008298 initialization and 0x800082c0 -> 0x8002ab90 directory scan.
  This all-pad scan is separate from the incremental insertion operation below.

0x80008dd8(pad, nameOrPath, selectNewEntry)
  Computes the pad catalogue and calls 0x80008138 with callback 0x80008f00.
  0x80008138 obtains a free slot (0x8002aaa8), strips directory components if
  supplied, and inserts the basename (0x8002a220). If requested, 0x8002af98 sets
  the current catalogue index. Finally it invokes the notification callback.
  Success returns 0; exhausted/invalid conditions can return -1.
  This is an in-memory insertion, not a file copy or disk existence check.

0x8002a220(catalogue, basename, internalIndex)
  Maintains the entry links, increments the entry count, copies the UTF-16 name,
  and marks the slot occupied. Checks include name length and a 1000-entry limit.
  The tests cover normal small catalogues, not limit/error-path robustness.

0x80008bd0(pad, suppliedPath)
  Acquires/releases a lock around its busy-state changes, extracts the basename,
  resolves it in the pad catalogue, constructs the pad-local full path, and calls
  0x8004b760(path,pad,index,count,0). Conditionally requests settings persistence.
  Missing entries skip assignment. A recorder path with a matching basename
  still resolves to the pad directory. This behavior is verified offline.

IMPLEMENTATION IMPLICATIONS

A first prototype should retain normal multitrack recording and wait for its
master to finish post-processing. Then copy that master to a unique name in one
pad folder, close and validate the copied file, insert it in that pad's catalogue,
and use the existing assignment/persistence mechanism. Keep the previous valid
assignment until copying and validation succeed. Report/handle a full card or
catalogue, failed copy, missing master and split recordings explicitly.

Do not implement this by merely changing the recording-target byte from -1 to a
pad number. That value participates in start/stop behavior and destination choice
for the whole post-processing path. Its effect on multitrack recording has not
been established. A separate post-record action is a better bounded experiment.

For the first on-device prototype, use one destination pad. The requested newest
on pad 1 / older on pads 2..4 ordering is another step: stock catalogues are per
folder, so changing assignment indices alone does not move a take across pads.
The initial copy approach also incurs processing time and additional storage.

REMAINING DECISIONS AND VERIFICATION

1. Recover the filesystem copy/close/error contract and the lifetime of finalized
   master paths, including split takes; locate a suitable worker/context after
   normal post-processing. Catalogue insertion alone does not complete this.
2. Verify stock pad playback during multitrack recording, backing inclusion in
   the master, clean channel stems, and practical count-in timing on hardware.
3. Confirm the exact processor, flash layout, update acceptance and a recovery
   route before installing any experimental firmware. Current evidence does not
   justify calling flashing safe or claiming a working custom firmware exists.
