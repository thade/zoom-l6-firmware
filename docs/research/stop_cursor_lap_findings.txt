Native arithmetic reproduction
The existing record-boundary audit identifies a 240,000-frame source ring and
native final-limit conversion at 0x800382a8. For each enabled stream it uses:
  consumed_frames + ((saved_stop_cursor - read_cursor) modulo capacity)
The earlier audit explicitly excludes arbitrary instruction-level preemption
and an in-flight producer fence. A modulo cursor does not identify its lap.

tests/emulation/verify_stop_cursor_lap.py executes the original conversion using
coherent synthetic cursor/count pairs. With the consumer 64 frames before or
exactly at the saved stop, the limit is 8,191,488. With stream 0's consumer
64 frames beyond it, its limit is 8,431,488 while other enabled streams retain
8,191,488. The one native-instruction group passes and reproduces the observed
excess exactly. Evidence: analysis/stop_cursor_lap_verification.json.

This demonstrates a mechanism capable of adding one ring if that state occurs.
It does not demonstrate the scheduling order on the device, an actual producer
crossing the saved stop, or causation by the held memory or diagnostic hooks.
No recorder-stop patch is justified or implemented from this evidence alone.

Button observation and priority (later user clarification)
The user recalls using Play/Stop for the affected take rather than Record.
The physical stop button was not recorded in the earlier test logs. This is a
specific hypothesis for later comparison, not a measured cause or proof of a
deliberate five-second tail. The user considers it a low-priority issue.

A bounded offline observation executes the original record-toggle 0x80034f40,
play-toggle 0x80034e58 and stop-request 0x80034d18 under recording state 1.
All three queue the same RecStop callback 0x8004ba41 with argument zero.
Under playback state 2, play/stop requests instead queue PlayStop 0x8004b911,
while the record toggle queues nothing. Static callback inspection also shows
both named stop callbacks save the endpoint using 0x80002460/0x80006918 and
enter the same backend 0x8000b698. The ordinary RecStop target is -1; PlayStop
passes -1 directly. There is no demonstrated separate five-second-stop policy.
Admission/mutex/queue effects are fixtures, and full physical-button ingress
and scheduling remain unobserved. Evidence: analysis/stop_request_paths_observation.json.

Defer further stop diagnostics and proceed first with the memory/storage budget.
Use the Record button as the consistent stop action for subsequent recording
trials and note the button used. The discrepancy stays open as a follow-up;
it does not block buffering development or independently justify a stock patch.
