EXPERIMENT 06: EXPLICIT CANDIDATE MEMORY RESERVATION
7 October 2026

Result
A capture-disabled trial is staged, its execution is confirmed after the
user-reported manual update, and one explicit reservation succeeds on hardware.
Normal boot does not reserve memory. One exact new editor-session command attempts the fixed candidate
allocation after normal startup; status queries remain read-only. This avoids
adding an optional allocation ahead of stock Main/card/pad initialization or
claiming that the earlier post-idle startup candidate provides later reserve.
No capture, task, audio/file/SD operation or pad mutation is enabled.

Allocation contract
The current capture ABI yields a 77,279-byte request for 128 slots. Separate
16,384-byte stack and 148-byte task-object requests mirror native task creator
allocation sizes without creating a task. The original allocator's usual split
charges are 77,288 + 16,400 + 160 = 93,848 bytes. Full-block consumption can add
up to 16 bytes per request. Require 159,432 free bytes before allocation to
retain the experimental 65,536-byte floor even with all three remainders.

The original allocator/free entries are 8006de78/80073f48. Both nest native
scheduler suspension 80074780/resume 80077540. The added outer suspension keeps
preflight, all allocations, the post-check and reverse-order rollback together;
it does not disable event sources or replace native pending-task/PendSV handling.
Native scheduler suspension is the word at 801f904c. Admission also requires
running flag 801f9048=1, initialized heap sentinel 801f901c=8095ffd0, current TCB
808e291c nonzero, Thread mode and clear BASEPRI/PRIMASK. No new RTOS task is added.

Successful pointer ownership lasts until reboot. Payloads are unused and never
zeroed. Partial failures free only newly obtained, unpublished allocations.
Current free bytes are restored on those failures; the historical minimum and
allocator counts need not be restored. One weak compare/exchange admits an
attempt without spinning; a missed claim leaves UNTRIED, an accepted failure is
terminal for the boot. Status publication is monotonic UNTRIED -> BUSY -> one
terminal status, so matching non-busy before/after reads identify stable fields.
The elapsed count excludes final native resume/scheduling. No heap-list scan,
arbitrary address/size, live release, allocation retry loop or reset is exposed.

Image and compatibility
Exact image SHA256 is c06f9d567eae7880fc704852e4f34d8053e55f13af7ce269056c4828baeb69b7.
Code/state occupy 2,624 bytes in the same audited diagnostic MAIN/DSP-source tail.
Persistent state totals 480 bytes, including 444 timing bytes, alignment and a
32-byte reservation record. Only the original diagnostic parser and SD/public
file prologue sites are patched. There is no boot or task-creator patch.
The shared parser assembly defaults to its original callback; only this build
selects the reservation dispatcher. Experiments 04 and 05 retain their exact
984-/1,756-byte builds and original hashes; all 25 prior diagnostic groups pass.

Verification
Fifteen groups execute the compiled trial and native allocation/free/suspend/
resume instructions. Success from 163,104 free bytes charges exactly 93,848 and
leaves 69,256. A deliberately fragmented native heap refuses the large request
despite 271,856 aggregate free bytes. Three actual unsplittable remainders charge
93,896 and leave exactly 65,536 at the preflight boundary. Null returns at each
allocation test exact rollback and no repeated attempt. Memory-write observation
confirms no reservation payload writes. Original unrelated occupied payloads,
protected MIDI reply lifetime and native file/SD results remain exact.
The existing native heap-backed capture suite also passes its 14 groups.

Critical-section effects, pending task lists, preemption/interrupt delivery,
storage sectors and DMA/cache behaviour retain fixture inputs. Pending PendSV
register writes run natively against simulated MMIO; no hardware exception is
delivered. These are software-contract checks, not measured device headroom or
allocator latency. The sandbox cannot map the emulator memory on this host;
the checks ran outside the sandbox. The exact image was staged/read-back verified
on the expected card, preserving settings and all 86 recording/pad entries;
all 30 saved audio evidence hashes were checked before and after. Safe unmount,
transfer exit, original pad/MIDI replies and normal Editor connection passed.
Hardware observations

budget, UNTRIED status and all seven reservation fields zero. Idle current and
historical minimum heap are both 163,104 bytes. All seven timing queries and
ordinary pad counts/assignments pass, the Editor connects normally, and all
three L6 MIDI ports remain available. Other connected instruments are excluded
from the L6 port comparison. This confirms diagnostic execution and installed
behaviour, not installed-flash bytes or recovery from broken firmware.

The existing GLORY_BOX.WAV was selected on pad 1 in Loop mode at 0 dB before
reservation; other pads and catalogue counts stayed unchanged. One explicit
kind-2 command obtains all three blocks. Its reply and a separate read-only

remain 1. Native scheduler suspension is zero in both replies. Reservation
elapsed work reports zero ticks, which does not establish wall-clock latency
or bound interrupt/scheduling effects. All retained timing observations are
consistent with no observed errors. The blocks remain unused and held.
