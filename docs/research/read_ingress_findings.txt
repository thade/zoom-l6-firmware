READ TRACKING CONNECTED TO COMPACT RELOAD INGRESS
4 October 2026

Result
rc_bind_reads now connects the producer and file-worker adapters to the SAME
coordinator and task contexts used by compact reload ingress. The combined test
runs rc_worker/rc_ui -> rt_receive/rt_run -> original reload/prefetch -> compiled
read dispatcher/callback -> original file worker with its compiled adapter.

Unlike earlier read tests, this test does not manufacture RT_RUNNING phases or
copy envelopes into task state. The compiled ingress and transport create,
claim, execute and complete those states from compact queue messages. All eight
initial reads acquire distinct tickets under the correct branch and root.

Cold binding
rc_bind_reads is optional and called after rc_bind, before admission or hook
activation. It requires a single initialization caller and quiescent queues.
It verifies:
- Both adapters use the exact ingress coordinator, task pointers and native IDs.
- Producer read slots match the file-worker table at both advertised indices.
- The file worker is distinct from assignment/Main, and its queue is distinct
  from their queues. Stock reload queue handles match the ingress binding.
- Existing adapter preflights accept native task/queue/semaphore handles and
  permanent configuration. Neither endpoint may already be bound.
- Coordinator/ledger locks and admission are idle, no reload job is live, both
  task contexts are initially idle, and every bound read slot is empty.

rp_can_bind and rw_can_bind perform read-only preflight. Both complete, along
with all cross-checks, before either binding is consumed. The adapter binders
then copy their configurations. An unexpected failure during that final sequence
faults the coordinator; there is no reset or rollback of permanent state.
This sequence is safe only under the single cold caller contract, not concurrent
initialization. RcBinding/runtime configuration must remain fixed thereafter;
their existing diagnostic fields can still change.

Invalid configuration, occupied state and prior endpoint binding are rejected
without consuming the other binding. This API does not install hooks, prove the
queues quiescent, or support hot cutover. The caller may activate read hooks only
after success. No startup installation site or allocation is selected here.

Shared stock receive boundary
The compact reload fixture intercepts stock receive entry 0x800483a8. Directly
using that address as the file adapter's receive port would route file work into
rc_next, which expects a reload worker/UI queue and task. rc_stock_receive now
replays PUSH {r4,lr} and resumes at 0x800483aa, retaining the original blocking
receive wrapper while bypassing the intercepted entry. The file-worker adapter
uses this forwarder; its sender uses the existing rc_stock_send forwarder.
These are compiled emulator forwarders, not installed branches or a placement
solution. Real RTOS queue operations remain fixtures.

6. Existing reload admission rejects late binding.
7. Occupied metadata, task and read-slot state rejects binding without a partial

8. A prebound producer or reader is detected before the other is consumed.

Test boundaries
Original reload producer/assignment/Main/prefetch/file-worker instructions and
compiled transports/read adapters share one CPU and memory. Scheduling uses
explicit register save/restore and a separate file-worker stack at yield points.
The fixture supplies native handles, call-entry/call-site redirection, kernel
queue copies, semaphore results, public file effects, WAV parsing and conversion.
It deliberately permits an early read-semaphore wake before actual completion.
Enclosing reload envelopes/phases now come from compiled ingress, not the fixture.

The bytearray storage, fixture scheduler and emulator instruction support do not
establish real SD timing/durability, IRQ/DMA behavior, physical memory placement,
chip identity or audio output. No device access, firmware patch or startup release
occurred. The separate capture-manager startup is not wired to these results.

Remaining work

and verified startup release with the actual memory/allocation constraints.
