Result
The examined successful handoff read/write paths do not require Main event
processing or the UI mutex. Initial audio reads and settings write/readback now
execute with the registered native SD dispatcher, command engine and event-wait
predicate on the SAME CPU fixture as the checked handoff and filesystem locks.
The native SD IRQ/event-post path uses a separate SD event object, not the UI
queue. This supports further investigation of the between-events candidate.

It does not enable the candidate: a reproduced native timeout still releases
software locks without proving physical controller/DMA completion. The current
adapter then attempts safe rollback in this fixture. That behavior cannot be
bound to hardware on public-return/lock-release evidence alone. Success also
does not resolve the previously documented acceptance of SD error-event bits.
The normal build remains without an input adapter or automatic gate binding.

What changed in the test boundary
Earlier handoff tests modeled filesystem driver reads as immediate logical file
byte copies. A separately compiled TEST fixture now submits synthetic one-sector
SD operations before invoking that same logical-byte model. It replaces driver
boundaries 0x80060818 and 0x800624a8 in the emulator only. It is not a recovered
filesystem-to-sector translator: block address, partial sectors, FAT/cache and
physical data are modeled. It allocates its own sector buffer to avoid making a
512-byte SD operation overwrite a smaller settings/header caller buffer.

The router executes original 0x80068378, the callback table recovered by original
startup decompression, read/write wrappers and actual command engine. Callback
addresses match the previously recovered eleven-entry table at 0x801f5ff0.
It is linked only into handoff-test.elf; profile verification rejects its symbols
from either normal capture-only or handoff build.

Dependency chain exercised
  checked handoff -> public filesystem wrapper -> filesystem domain ownership
  -> synthetic sector mapping -> original SD dispatcher -> per-unit token
  -> original command wait (0x183) -> data wait (0x185)
  -> final-status command wait (0x183) -> per-unit unlock
  -> modeled logical bytes -> filesystem unlock -> pad conversion/settings.

The wait wrapper 0x800328c0 reaches original event predicate 0x800326c0. Native
event masks and timeout 5000 are observed from actual arguments. MMIO responses,
event arrival, kernel time and critical-section endpoints remain fixtures.
Both initial sample reads and settings writes/readback retain the filesystem
domain through the SD waits. Sample prefetch also retains scratch ownership.
Pending command/data waits preserve all those owners and the handoff gate.
No Main event service is invoked to advance the waits.

The UI token is deliberately unavailable in these tests: an attempted take
would suspend the CPU and be recorded; releasing it would fail the test. Neither
occurs on the examined successful paths, including a larger multi-chunk initial
load with more than 500 synthetic sector operations. Main event receive, send,
enqueue, dispatch and targeted-delete entry calls also fail the fixture if used.
Open/close driver bytes, catalogue effects, conversion, gate and seal remain
models. The absence of a dependency here is not a proof about those boundaries
or every possible filesystem callback.

SD interrupt independence
Original IRQ 0x8006ea90 -> 0x8006ea98 decodes a modeled data-completion status,
then calls 0x80032828 -> 0x800324b0. That original event-post body writes the SD
event flags and calls kernel ISR give 0x80076628 with the SD event's token. The
fixture models that kernel wake endpoint, not a native interrupt preemption.
The event object at HOST+4 and its token differ from the UI mutex and queue.
This runs without Main dispatch or UI-mutex access. It does not prove DMA/cache
coherence or that the modeled completion status has the required physical meaning.

Timeout counterexample and binding rule
The fixture withholds a sample data event, then makes the kernel wait report
timeout. Native driver returns an error, its unit token is given, public wrapper
returns, and the existing checked adapter rolls back and releases the gate.
No controller-idle/reset observation has occurred. This reproduces the relevant
control flow in the combined fixture; it is not a real mixer fault.

The BackingGate contract now explicitly covers NEW native I/O during handoff as
well as preexisting users. A future gate cannot meet that contract merely by
joining old readers before entry and checking software locks afterward. It must
retain command/data errors and prove transfer completion or checked cancellation
before any safe rollback, close, buffer reuse or admission release. A timeout
deadline by itself cannot authorize any of those actions.

Simply retaining a file handle is insufficient if the transfer may still write
to a caller's stack or the shared prefetch buffer. Adding a wrapper that returns
UNCERTAIN after releasing those lifetimes would not fix the physical problem.
The existing gate remains unbound. Do not turn the diagnostic result into a
hardware-safe rollback claim or add a terminal Main wait as an automatic fix.

Next concrete work
Identify a native transfer-completion/error observation that covers command,
data and status work; preserve raw error events even when stock code returns
success. Then establish checked timeout cancellation/controller-idle semantics
before binding safe failure recovery. Native between-events wakeup and serialized
manager ownership also remain necessary. UI-mutex independence of the tested SD
chain removes one concern; it does not substitute for those proofs.
